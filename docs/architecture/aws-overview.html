The embedding Lambda runs an embedding model that turns text into numbers. It cannot write or judge text, so fit analysis and the AI resume rewrite use a language model on the school's SoCLaaS gateway, called from one shared LLM worker outside the VPC.

Fit analysis flow

  1. The web app calls POST /v1/jobs/{id}/fit-analysis. The API Lambda checks the monthly slot (free 5, premium 50), adds a fit_analyses row marked pending, and writes llm-requests/<analysis_id>.json (task: fit) to the private documents bucket. The file holds the job text, the job's cached requirements (if any, from job_requirements) and the profile evidence text, so the worker needs no database.
  2. The S3 event starts the LLM worker Lambda (one worker for every AI task; reserved concurrency 5). It runs outside the VPC with no database access, and uses the same container image as the API with the handler job_hunter.llm_worker.handler.
  3. The worker calls the SoCLaaS gateway (soclaas-api.comp.nus.edu.sg/v1, model ornith1.5:35b) over the public internet: extract requirements, judge each one against the profile, suggest improvements.
  4. The worker writes llm-results/<analysis_id>.json to S3. Request and result files expire after 1 day.
  5. The web app polls GET /v1/fit-analyses/{id}. The API Lambda reads the result and checks it again: it drops invented evidence ids and numbers and works out the coverage percentage in code. It then saves the result in Aurora (fit_analyses, per-user row-level security) and caches the job's requirements in job_requirements, shared by all users.

About 28 to 39 seconds and roughly USD 0.0008 per analysis in the benchmark. Embeddings still only rank jobs for "For you".

Job pull flow

  1. Someone runs the Pull jobs workflow in GitHub Actions (or, if switched on, the EventBridge schedule fires). It invokes the Discovery Lambda with the batch size (default 10 new jobs). The workflow refuses to run while staging is paused.
  2. The Discovery Lambda runs outside the VPC, so it can reach the public job feeds: Greenhouse and Lever boards, MyCareersFuture searches and, once the two Adzuna keys exist, Adzuna. It keeps Singapore jobs only and writes them as one snapshot, imports/<pull_id>.json, in the documents bucket.
  3. It then invokes the Import Lambda directly and waits. The Import Lambda runs inside the VPC and reads the snapshot over the free S3 gateway endpoint. The database cannot be reached from the internet side, and the internet cannot be reached from the database side.
  4. The Import Lambda mixes the sources so a small batch is not all one employer, inserts the next N jobs that are not stored yet, and refreshes the ones that are. Each source keeps its own row, so running the pull again never creates repeats.
  5. Duplicate detection: a posting found on two sources is linked, not deleted. The employer's own board wins over MyCareersFuture, which wins over Adzuna. Discover shows the winner once, with "Also on MyCareersFuture". Two rows are linked only if the employer, title and place match and the descriptions are nearly the same text, or they share the same listing link. On the labelled test set of 16 pairs this gives no wrong links and finds all 8 true duplicates.
  6. After the commit the Import Lambda writes an embed flag, and the existing embed worker gives the new jobs vectors a few minutes later. The counts come back to the workflow summary.

A pull wakes Aurora (it pauses when idle), so run it when jobs are needed. Adzuna only returns a short snippet of each description, so jobs found only there may be too short for fit analysis, which needs 120 characters.

AI resume rewrite flow

  1. On a resume page, "Tailor with AI" calls POST /v1/documents/{id}/tailor with mode: ai. The API makes the rule-based tailored copy first, then writes a task: tailor request to llm-requests/ with the resume bullets and the job's title, skills and description.
  2. The same LLM worker rewrites the bullets and writes the result file. This takes about 5 to 10 seconds, so the API waits for it inside the request, for at most 25 seconds.
  3. The API keeps only the rewrites that add no new number or name, and spends the month's slot only if at least one bullet changed.
  4. If the worker is slow, fails or has no key, the user gets the rule-based copy and a message. Nothing is charged.

Why it is shaped this way

  • No internet inside the VPC. A NAT gateway or interface endpoints cost money, so anything that needs the internet sits outside, and anything that only needs the database sits inside.
  • Background work starts with a small file in S3. The S3 gateway endpoint is free, and an S3 event then wakes the worker. The embedding worker already works this way.
  • Job discovery is split in two for the same reason. One function can either reach the job feeds or reach the database, never both, so the one that reads the feeds sits outside the VPC and the one that writes the database sits inside. They are joined by a small file in S3 and a direct call, which leaves the bucket's single notification slot to the embed and LLM workers.
  • The embedding model is baked into its container image. It is small, so the embed Lambda needs no network to run it.
  • The language model is hosted by the school. The AI features call the SoCLaaS gateway, so no model is stored on AWS. One shared worker outside the VPC makes the calls for every AI feature and has no database access; the API Lambda checks its answer before saving or using it. A new AI feature adds a task to the worker, not a new Lambda.
  • Slow work is asynchronous. API Gateway waits at most 29 seconds and an analysis takes 28 to 39 seconds, so the API returns at once and the web app polls for the result. The resume rewrite takes 5 to 10 seconds, so the API waits for it inside the request, for at most 25 seconds.
  • Amazon Bedrock is not used. The group's AWS account has a service control policy that denies model invocation.
