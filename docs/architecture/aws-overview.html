The embedding Lambda runs an embedding model that turns text into numbers. It cannot write or judge text, so fit analysis uses a language model on the school's SoCLaaS gateway, called from a small worker outside the VPC.

Fit analysis flow

  1. The web app calls POST /v1/jobs/{id}/fit-analysis. The API Lambda checks the monthly slot (free 5, premium 50), adds a fit_analyses row marked pending, and writes fit-requests/<analysis_id>.json to the private documents bucket. The file holds the job text, the job's cached requirements (if any, from job_requirements) and the profile evidence text, so the worker needs no database.
  2. The S3 event starts the fit-worker Lambda. It runs outside the VPC with no database access, and uses the same container image as the API with the handler job_hunter.fit_worker.handler.
  3. The worker calls the SoCLaaS gateway (soclaas-api.comp.nus.edu.sg/v1, model gemma4:26b) over the public internet: extract requirements, judge each one against the profile, suggest improvements.
  4. The worker writes fit-results/<analysis_id>.json to S3. Request and result files expire after 1 day.
  5. The web app polls GET /v1/fit-analyses/{id}. The API Lambda reads the result and checks it again: it drops invented evidence ids and numbers and works out the coverage percentage in code. It then saves the result in Aurora (fit_analyses, per-user row-level security) and caches the job's requirements in job_requirements, shared by all users.

About 28 to 39 seconds and roughly USD 0.0008 per analysis in the benchmark. Embeddings still only rank jobs for "For you".

Why it is shaped this way

  • No internet inside the VPC. A NAT gateway or interface endpoints cost money, so anything that needs the internet sits outside, and anything that only needs the database sits inside.
  • Background work starts with a small file in S3. The S3 gateway endpoint is free, and an S3 event then wakes the worker. The embedding worker already works this way.
  • The embedding model is baked into its container image. It is small, so the embed Lambda needs no network to run it.
  • The language model is hosted by the school. Fit analysis calls the SoCLaaS gateway, so no model is stored on AWS. A small worker outside the VPC makes the call and has no database access; the API Lambda checks its answer before saving it.
  • Slow work is asynchronous. API Gateway waits at most 29 seconds and an analysis takes 28 to 39 seconds, so the API returns at once and the web app polls for the result.
  • Amazon Bedrock is not used. The group's AWS account has a service control policy that denies model invocation.
