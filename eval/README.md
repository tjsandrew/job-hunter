# System evaluation tooling

Scripts and results for the system evaluation committed to in the preliminary report, section 4.2. Most scripts run against **staging**; deduplication and cost scripts run offline. Load tests share staging with real users, so run them in an agreed window.

## Evaluation accounts

Six Cognito accounts, `jh-eval-01@example.com` to `jh-eval-06@example.com`:

- **Addresses:** `example.com` is a reserved domain, so no one receives mail. Invitation emails are suppressed.
- **Plan:** all are on the free plan, with 5 AI uses a month each.
- **Personas:** each holds one fictional profile, confirmed, with job preferences.

| Account | Persona | Preferred roles |
|---|---|---|
| jh-eval-01 | Data Engineer | Data Engineer |
| jh-eval-02 | Backend Software Engineer | Software Engineer, Backend Engineer |
| jh-eval-03 | Data Analyst | Data Analyst, Business Analyst |
| jh-eval-04 | Frontend Developer | Frontend Developer, Software Engineer |
| jh-eval-05 | Cloud and DevOps Engineer | DevOps Engineer, Cloud Engineer |
| jh-eval-06 | Business Analyst | Business Analyst, Product Analyst |

**Passwords** are generated by `seed_accounts.py` and stored only in `~/.job-hunter-eval/accounts.json` (mode 600) on the machine that created them. They are never committed or printed. The script has no count or range argument. To change the seeded personas, edit `PERSONAS`; operators can reset a password with `admin-set-user-password`.

**Work modes are left empty.** Only the Lever source states a work mode (11 of 1,084 listings on 25 October 2026), and the eligibility rules exclude jobs with an unstated work mode whenever any mode is selected. With work modes set, each persona saw about 10 jobs; with them empty, 149–236 of the 309.

```sh
# Create any missing accounts and seed any unseeded ones (needs an operator SSO session and boto3).
AWS_PROFILE=<sso profile> python eval/seed_accounts.py
# Sign every account in and call /me.
python3 eval/cognito_tokens.py
```

**After the project,** delete the accounts. Their profile data stays in Aurora until the database is removed; use each account's "Delete profile data" first if it should go sooner.

```sh
for n in 01 02 03 04 05 06; do
  aws cognito-idp admin-delete-user --user-pool-id ap-southeast-1_rqE5iKEpf --username jh-eval-$n@example.com
done
```

## Tokens

`cognito_tokens.py` signs in through the same authorization-code + PKCE flow as the web app, by submitting the classic managed login form of our own user pool. Password sign-in (`USER_PASSWORD_AUTH`) is not used: its tokens lack the `jobhunter/use` scope the API requires.

- `login(email, password)` returns access, ID and refresh tokens.
- `refresh(refresh_token)` returns a new access token. Access tokens last 60 minutes and refresh tokens 1 day.

## Load tests

`locustfile.py` uses the evaluation accounts, refreshing tokens before they expire. It never calls the AI endpoints.

| User class | Used for | Behaviour |
|---|---|---|
| `BaselineUser` | B1 responsiveness | One user cycling evenly through `/me`, All jobs, For you, job detail, saved jobs, tracker, profile, profile bank and documents |
| `BrowsingUser` | B3 scalability | A weighted session: All jobs and For you ×3, job detail ×3, and `/me`, saved jobs, tracker, profile bank and Save/Pass ×1 each, with 1–3 s pauses |

Failures are labelled `429 throttled` (the deliberate gateway and Lambda caps), `5xx server error`, `401 auth` or `HTTP <code>`.

```sh
python -m venv .venv-eval && .venv-eval/bin/pip install -r eval/requirements.txt
# B1: per-endpoint baseline, one warm user.
.venv-eval/bin/locust -f eval/locustfile.py BaselineUser --headless -u 1 -r 1 -t 10m --csv eval/results/b1-baseline
# B3: step load 1 -> 10 -> 50 -> 100 users, 5 minutes each. Agree a window with other operators first.
EVAL_STEPS=1,10,50,100 EVAL_STEP_SECONDS=300 .venv-eval/bin/locust -f eval/locustfile.py BrowsingUser \
  --headless --csv eval/results/b3-run1 --csv-full-history
```

A smoke test on 25 October 2026 (1 baseline user for 45 s, then 2 browsing users for 30 s) passed every endpoint, including the Save/Pass write, with no failures. From those few samples, All jobs and For you took about 1.3–1.5 s at the median and the other reads about 80–120 ms. That is indicative only, not a B1 result.

## Load-test capacity window

Run B3 twice:
- **run 1** at the normal staging limits;
- **run 2** in a short, announced window with the limits raised.

| Limit | Normal | Window | How |
|---|---|---|---|
| API Lambda reserved concurrency | 10 | 50 | `put-function-concurrency` (Terraform ignores it after creation) |
| Gateway rate / burst | 20 / 40 per second | 200 / 400 | `-var gateway_rate_limit=… -var gateway_burst_limit=…` |
| Aurora maximum capacity | 1 ACU | 4 ACU | `-var aurora_max_acu=4` |

Lambda headroom: the account allows 400 concurrent executions, and AWS keeps at least 100 unreserved. The functions reserve 20 today (API 10, LLM 5, embed 2, discovery 1, import 1, migrate 1), so 50 for the API leaves plenty.

Raising the limits with `-var` makes staging differ from `main` until it is restored, and anyone who applies during the window undoes it. So:

1. Agree a two-hour window without applies or deploys with the other operators. Check that no Deploy staging or Pull jobs run is in progress.
2. Record the starting state in `eval/results/<run>/config-before.txt`: `get-function-concurrency` for the API, the stage throttles (`aws apigatewayv2 get-stage`) and the Aurora scaling (`aws rds describe-db-clusters`).
3. Raise the limits:
   ```sh
   aws lambda put-function-concurrency --function-name jobhunter-staging-api --reserved-concurrent-executions 50
   terraform -chdir=infra/aws apply -var-file=staging.tfvars \
     -var aurora_max_acu=4 -var gateway_rate_limit=200 -var gateway_burst_limit=400
   ```
   The plan must show only the stage throttles and the cluster's `max_capacity`. The capacity limit changes online; a change to the derived `max_connections` parameter needs a reboot.
4. Run B3 run 2, and keep the CloudWatch metrics for the window: Lambda `ConcurrentExecutions` and `Throttles`; Aurora `ServerlessDatabaseCapacity` and `DatabaseConnections`.
5. Restore the same day, then confirm that a normal plan shows **No changes** and that reserved concurrency is back to 10:
   ```sh
   terraform -chdir=infra/aws apply -var-file=staging.tfvars
   aws lambda put-function-concurrency --function-name jobhunter-staging-api --reserved-concurrent-executions 10
   ```
6. Record the end state in `config-after.txt` and notify the other operators that the window is closed.

At 4 ACU, Aurora costs about USD 0.80 an hour while it is fully used. A 2-hour window costs about USD 1–3 in total.

## Results index

A6 covers acceptance checks; B1–B5 cover responsiveness, AI timings, scalability, ingestion and cost respectively.

Each result folder has a `notes.md` with the findings and how they were measured. Scripts that read AWS need an
operator SSO session (`AWS_PROFILE=...`); all run from the repository root in the evaluation virtualenv.

| Part | What | Script | Results |
|---|---|---|---|
| A6 | Isolation and token checks (26 passed, 1 informational), expired-token check, Aurora pausing, pause/resume workflow | `acceptance.py` | `results/a6-*` |
| B1 | Responsiveness of the browse endpoints, one warm user | `locustfile.py BaselineUser`, `analyse_b1.py` | `results/b1-baseline-20261025/`, `results/b1-baseline-20261027/` (after the ranking speed-up) |
| B2 | AI task timings and token counts; rewrite re-run after the shape fix ([PR #33](https://github.com/tjsandrew/job-hunter/pull/33)) | `b2_ai_tasks.py`, `analyse_b2.py` | `results/b2-ai-tasks-20261025T130734Z/`, `results/b2-ai-tasks-20261025T184828Z/` |
| B3 | Step load 1 → 100 users at the normal limits (run 1) and in the raised-capacity window (run 2) | `locustfile.py BrowsingUser`, `analyse_b3.py` | `results/b3-run1-20261026/`, `results/b3-run2-20261026/` |
| B4 | Job pulls (volume, failures, stage times) and duplicate-removal accuracy on 84 labelled real pairs | `b4_pull.py`, `analyse_b4.py`, `dedup_eval.py` (pairs in `dedup/staging_pairs.json`) | `results/b4-pipeline-20261026/`, `results/b4-dedup-20261026/`, `results/b4-pulls/` |
| B5 | Actual spend for 1–25 October 2026 and the cost model against workload, with the break-even chart | `cost_model.py` | `results/b5-cost-20261026/` |

```sh
# B2 (spends one AI use per account and job; announce first)
python eval/b2_ai_tasks.py
AWS_PROFILE=... python eval/analyse_b2.py eval/results/b2-ai-tasks-<stamp>
# B4: one more measured pull (run once or twice a day), then re-tally every pull on record
AWS_PROFILE=... python eval/b4_pull.py 10
AWS_PROFILE=... python eval/analyse_b4.py
python eval/dedup_eval.py          # offline, no AWS
python eval/cost_model.py          # offline; prices and assumptions are parameters at the top
```

The load tests must run with the laptop awake and its lid open for the whole run (`caffeinate` keeps it from idling
to sleep, but closing the lid still sleeps it); the first B3 attempt was lost that way.
